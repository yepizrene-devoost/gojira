## Specs

- S1: "y no deberiamos poder hacer lo mismo en las tres superficies? o tener las mismas opciones?", "pero igual deberian poder tener capacidades pares a CLI y TUI para poder hacer lo mismo pero de forma visual". The TUI must be able to edit summary, priority and labels like `gojira update` and the MCP `gojira_update` tool.
- S2: "hacia develop", "dale". One branch per parity unit, finished into develop; the maintainer approved starting this unit (the TUI field editor) after it was proposed as the next one. Issue #30 stays open.
- S3: In the ticket detail (opened from a board card or from search results) the `U` key opens a bounded form for Summary, Priority and Labels, prefilled from the current ticket. Tab and Shift+Tab move between the three inputs, Ctrl+S saves, Esc cancels without any request, Ctrl+C quits, pasting works. It is a separate flow from `E` (due date, components, fix versions, story points) and from `e` (description); the `E` flow and its asynchronous story-points loading stay untouched.
- S4: Only changed fields are sent. No change closes the form with no request. Emptying Summary or Priority, or clearing all labels, is an inline validation error with no request (the CLI and MCP cannot clear them either); label entries are comma-separated, trimmed and must not be empty. The payload is built by the shared `issuefields` package, so it is exactly what `gojira update` sends (`summary` string, `priority` as `{"name": ...}`, `labels` array), with no edit-metadata request (same as the CLI and MCP for these fields).
- S5: One accepted save sends exactly one `UpdateIssue` and one detail refresh, never retried automatically; repeated keys while it is in flight start nothing; Esc leaves the form and invalidates the reply but cannot cancel a request already sent; a late reply after Esc, another ticket, another board or another search is discarded. If the update is applied but the refresh fails, the form says so and Ctrl+S retries only the refresh, never the update. Errors are shown inline and keep the typed text.
- S6: After a successful save the detail shows the refreshed ticket with a toast, and the board card (or search result row) of that ticket shows the new summary, priority and labels without a full reload.
- S7: Strict TDD and strict SOLID (standing preference). Per rule one observed behavioral RED, then GREEN; tests assert requests sent (path and exact body), view contents, state transitions, and zero requests on cancel, no change and invalid input; one regression test per touched existing behavior; every existing TUI test stays unmodified and passing. `internal/tui` stays ONE Bubble Tea model with plain state switching. New behavior lives in new small files; `tui.go` receives only the minimum wiring and is not reformatted (`gofmt -l` already lists it). Help overlay, footer and README ship with the behavior. Work stays unstaged and uncommitted for maintainer review (AGENTS.md).
- S8: Out of scope: a priority picker populated from Jira, clearing labels, merging this form into `E`, TUI JQL search, project list, user search, reports, export, MCP assign by email, create options (with #24), and deduplicating the TUI close/reopen logic.
