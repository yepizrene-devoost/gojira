# Issue 23 — second delivery: project context, `init`, `context` and interactive picker

Implements tracks 1-2 of [issue #23](https://github.com/yepizrene-devoost/gojira/issues/23) plus the MCP `gojira_context` tool. Design source: `odd/tasks/issue-23-agent-first-access.md`. Branch `feature/issue-23-project-context`. Nothing is committed, staged or reviewed without an explicit user instruction.

## Specs

- S1: "resolution order: flag > environment variable > `git config gojira.project` (read with `git config --get`, never by parsing the file, so worktrees and submodules work) > user-level config." Environment variable: `GOJIRA_PROJECT`. User-level config: the existing `default_project` (`gojira config set project KEY`). An unset or empty value falls through; a non-empty value that is not a Jira project key (`^[A-Z][A-Z0-9_]*$`) fails with a `validation_error` naming its source, never a silent fallback. Git missing, not a repository, or key unset all mean "unset", not an error. The git source also reports its scope (`local`, `global`, `worktree`) from `git config --show-scope`.
- S2: "`gojira context --json` — reports the resolved project, where it came from (flag, env, git, user) and the authenticated identity. When no project is configured it returns a machine-readable result so an agent asks the human instead of guessing." Success shape: `{"schemaVersion":"v1","project":{"key","source","scope?"}|null,"needsProject":bool,"identity":{"accountId","displayName","active"}}`. No project is exit 0 with `project:null,needsProject:true`. No email and no token are ever printed. Identity comes from `GET /rest/api/3/myself` (constant in `internal/jira/paths.go`). Authentication or network failures use the existing error envelope; no identity is fabricated. A `--project` flag provides the `flag` source. Human output is a short readable summary.
- S3: "`gojira init` stores `[gojira] project = KEY` in the local, untracked `.git/config` of the current clone; with a terminal it shows a **list of projects to pick from** instead of a free-text field; without a terminal it accepts `--project KEY --yes` so an agent can run it. No secrets are ever stored there." Writes with `git config --local gojira.project KEY`. Outside a git repository it fails with a `validation_error` and writes nothing. `--project KEY` skips the picker; without a terminal `--yes` is required, otherwise a `validation_error` with zero requests and zero writes. The key is verified against Jira (`GET /rest/api/3/project/{key}`) before writing. After writing, the effective resolution is read back and, if a higher-priority source (environment variable or a worktree override) still wins, the command says so instead of implying the new value is in force. `--json` returns `{"schemaVersion":"v1","project":KEY,"written":"local","effective":{"key","source","scope?"}}`.
- S4: Interactive picker (new package `internal/picker`, standalone Bubble Tea v2 model, separate from the single TUI model in `internal/tui`): lists `KEY  Name`; arrows (and `k`/`j`) move; typing filters by key or name case-insensitively; Enter selects the highlighted entry; Esc or Ctrl+C cancels and `init` then writes nothing and exits non-zero with a plain message; the viewport scrolls with a bounded visible window; an empty filter result says so and Enter selects nothing; terminal resize is honored. It only runs when stdin and stdout are terminals.
- S5: Complete project list: `Client.GetProjects()` paginates `GET /rest/api/3/project/search` (`startAt`/`maxResults`, `isLast`) with a documented safety cap and a repeated-page guard, instead of the single non-paginated `/project?maxResults=100` request. `gojira projects` output for accounts with up to 100 projects is unchanged. The pagination contract must be verified read-only against the real Jira before relying on it.
- S6: MCP: add a no-argument read-only tool `gojira_context` returning the same object as S2, using the shared function (no CLI shell-out). Resolution there uses the server process's working directory and environment; the guide and tool description say so and that an absent project means ask the human. The fixed read-only allowlist grows from five to six tools; no write tool is added.
- S7: Existing commands keep their behavior: `create --project`, `search`, `backlog` etc. are not wired to the resolver in this delivery. `default_project` becomes consumed only by `context`/`init` logic. `config init`, `config set/get project` are unchanged.
- S8: Zero artifacts: nothing is written to the repository tree; only `.git/config` (local, untracked) through `git config`. README documents `init`, `context`, the resolution order, the Git scope caveat (global and worktree scopes can override) and the MCP tool.
- S9: Tests first (RED observed), httptest and temporary git repositories only: resolver precedence table; empty and invalid values; git outside a repo, missing git binary, linked worktree, submodule, global versus local scope; `init` non-TTY refusals with zero requests and writes; successful non-interactive write and readback; `context` with and without project, identity shape, no email in output, auth failure envelope; project pagination across pages, safety cap and repeated page; picker `Update` tests (navigation, filter, select, cancel, empty, scrolling, resize); MCP tool listing now six, read-only annotations, shape; existing `projects` output differential check against the previous code. `go vet`, `go test ./... -count=1`, `golangci-lint run ./...` and the new tests under `-race` must pass.
