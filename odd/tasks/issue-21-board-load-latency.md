# Issue #21 — reduce TUI board load latency

Opening a board in the TUI takes ~2-11 s because `loadBoardData` downloads every issue of the board, serially, only to compute the Backlog column. Chosen design: option A (keep today's Backlog column contents, fetch them faster). GitHub source of truth: [issue #21](https://github.com/yepizrene-devoost/gojira/issues/21).

## Specs

- S1: Add `Client.GetBoardBacklog(boardID)` using `GET /rest/agile/1.0/board/{id}/backlog` (path constant in `internal/jira/paths.go`), paging like `GetBoardIssues` (`maxResults=100`, `startAt`, same `fieldsBasic`, same safety cap). Jira's docs mark this endpoint deprecated; it was verified to work on the user's real site and returns a strict subset of today's Backlog column.
- S2: Today's Backlog column also contains issues that sit in FUTURE sprints (verified: 2 and 49 such issues on two real boards). Keep them: list future sprints with the existing `GetSprintsByState(boardID, "future")` and read each one's issues with `GetBoardIssues(boardID, sprintID)`. Exclude Done-category issues as today and de-duplicate by key against the active-sprint issues and the backlog issues. Column order: Jira-ranked backlog issues first, then future-sprint issues in sprint order.
- S3: In `loadBoardData` (`internal/tui/tui.go`), when an active sprint exists, stop calling `GetBoardIssues(board.ID, 0)` (the full-board download). Run independent requests concurrently with `sync.WaitGroup` or equivalent: config and sprints together; then active-sprint issues, backlog, and future-sprint issues together. No shared mutable state between goroutines; every goroutine writes its own result variable.
- S4: Error semantics stay as today: config, sprints or active-sprint issue failures fail the load (`result.err`); backlog and future-sprint failures are best-effort and must not break the sprint view. If the backlog endpoint fails (any error), fall back ONCE to the legacy computation (`GetBoardIssues(board.ID, 0)` minus sprint issues minus Done) so the column content is still complete; if that also fails, show the sprint view without a Backlog column, as today.
- S5: The branch without an active sprint (`GetBoardIssues(board.ID, 0)` for the whole board) is unchanged in this unit.
- S6: `boardLoadMsg`, request-id scoping, stale-result handling and the rest of the TUI flow are unchanged. Single Bubble Tea model; no sub-model routing. Endpoints only in `internal/jira/paths.go`.
- S7: README: short note that the Backlog column is read from Jira's backlog endpoint plus future-sprint issues, that the endpoint is documented as deprecated, and that the app falls back to the full-board computation if it fails. No live-Jira claim beyond what was measured and recorded in the Log.
- S8: Tests (RED first, httptest only): backlog client paging and path; with an active sprint and a working backlog endpoint, the unscoped `/board/{id}/issue` is NEVER requested; future-sprint issues are included, Done ones excluded, duplicates removed, column order as in S2; backlog failure triggers exactly one fallback to the legacy computation with the same resulting column; backlog and future-sprint failures plus fallback failure still deliver the sprint view; requests overlap (track max in-flight >= 2 using a server that blocks briefly, not wall-clock assertions); existing `loadBoardData`/board tests still pass. `go vet`, `go test ./... -count=1`, `golangci-lint run ./...` green.

- L4: Acceptance target: a board with ~1,800 issues loads in about 3 s or less (baseline 11.1 s) with the Backlog column holding the same issues as before; measured after implementation (I21-2).

- L6: Result (read-only, real Jira, real `loadBoardData`, two rounds, 7 boards): load time went from 2.2-11.1 s to 0.6-2.0 s. The ~1,840-issue board went from 11.1 s to 1.6-2.0 s; the ~1,670-issue board from 10.7 s to ~1.0 s. Backlog column equivalence against the legacy computation (all board issues minus active-sprint minus Done) checked by issue key on all 7 boards: legacy == new, 0 missing and 0 extra (sizes 11, 0, 3, 21, 61, 5, 25). Acceptance target (L4) met.
- L7: Verification: `go vet ./...`, `go test ./... -count=1`, `golangci-lint run ./...` green. `go test ./internal/jira -race` green and the new board-load tests are race-clean. `go test ./internal/tui -race` fails ONLY in `TestCommentEntry` and `TestLifecycleDeleteFailures`, which also fail on `develop` before this unit (the test servers write a variable the test reads without synchronization; production code is not involved and CI does not run `-race`). Tracked as separate follow-up, not part of #21.
- L8: Known limits: future-sprint issues are read sequentially in one goroutine (a board with many future sprints could make that the critical path); the backlog endpoint is documented as deprecated, so the legacy full-board fallback stays; the no-active-sprint branch is unchanged and still downloads the whole board serially.
