# CLI, MCP and TUI business-capability parity
Issue #30; branch `feature/interface-parity`; baseline `e3b83440b1e2e1b93e543ae4f3e5e8417a302237`.
Delivery: bounded work units, ask-on-risk; no staging/commits/push/RDD without explicit approval. Runner: Go tests with isolated HTTP servers and model messages, no live Jira/keychain/config.

## Specs

- S1: "y no deberiamos poder hacer lo mismo en las tres superficies? o tener las mismas opciones? porque por ejemplo CLI es usado por Agentes y humanos de forma programatica, MCP por agentes pero igual deberian poder tener capacidades pares a CLI y TUI para poder hacer lo mismo pero de forma visual". Target equivalent business operations and options, not identical UI syntax. Use shared business logic and surface-specific adapters. The matrix must distinguish implemented, partial and absent capability/option coverage.
- S2: "ok hagamoslo, crea el issue e inicia con la implementación, el issue agrega prioridad media, y approved desde el inicio lo asignas a mi y comienzas con esto". Create a feature issue with `priority:medium`, `status:approved` and the authenticated maintainer as assignee, then begin implementation. Record remote readback evidence.
- S3: Editable fields must cover existing CLI capabilities across adapters: summary, description, priority, labels, due date, components, fix versions and explicit story-points field/value. Preserve existing omission/empty-clear semantics and field metadata validation; plain description becomes ADF. No new Jira planning defaults. Test each added rule before implementation through the public adapter, plus existing update behavior and rejected-input zero-mutation cases.
- S4: Assignment must be available visually in TUI as well as existing CLI email/MCP account-ID paths. Reuse Jira identity resolution and AssignIssue; preserve the single Bubble Tea model. A missing/failed identity lookup must not assign, cancellation must not submit, and one accepted submission must not trigger automatic retry. Async results must stay scoped to their originating ticket/board.
- S5: Remaining parity includes create inputs and current planning/parent options, sprint/backlog and lifecycle operations, user selection, search/read completeness, reports and export data. Preserve existing CLI/MCP JSON fields, error/state semantics, opt-in MCP writes, confirmation safeguards and no mutation retries. Setup/output/navigation differences are not gaps. Do not claim full parity while any business-option row remains partial.
- S6: Standing user constraint: strict TDD and SOLID. Per-rule RED before production change, GREEN after; tests use isolated state and assert payloads, outputs/errors, unchanged mutation counts on rejection, and existing behavior. Help/docs ship with each behavior. Work stays unstaged/uncommitted for maintainer review (AGENTS.md). No live credential-store, configuration or Jira access in tests.
- S7: Issue #24 owns deliberate future issue-type discovery/planning-default/hierarchy changes. This issue aligns existing operations without silently implementing those changes. `/myself` authentication, OAuth and unrelated refactors are out of scope. About 400 authored diff lines per unit is advisory, not a reason to omit tests or compress code.
