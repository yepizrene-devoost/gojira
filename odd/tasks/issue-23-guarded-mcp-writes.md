# Issue 23 — guarded MCP writes
Opt-in write tools for `gojira mcp`, with server-enforced confirmation for destructive actions.
Implementation authorized; leave changes unstaged and uncommitted for user review.

## Specs

- S1: "la 1 pero con confirmación para tareas destructivas como borrar un ticket". Option 1 was: "Activación al arrancar con `--allow-writes`: da autoridad amplia a todas las herramientas de escritura habilitadas y confía en la confirmación del cliente." Ordinary write tools register only when the server starts with `--allow-writes`; without the flag the server stays read-only exactly as today (same tool list, no write tool callable).
- S2: Destructive actions (delete ticket) require confirmation enforced by the server, not only client behavior or tool annotations. Proposed mechanism for the design to refine: a first call returns a preview and a single-use, short-lived confirmation token bound to the exact action and issue; only a second call carrying that token executes. A call without a valid token never mutates.
- S3: Write tools reuse the existing application operations and the CLI mutation-state contract: `applied` / `not_applied` / `unknown`. An `unknown` outcome is never retried automatically and the result says so. Errors are sanitized like the existing tools (no Jira body, no URLs).
- S4: Ticket and comment text is untrusted data. Prefer comment/append over replacing a rich ADF description; if a replacement is offered it states the formatting loss. Annotations are accurate hints (`readOnlyHint=false`; `destructiveHint=true` for delete) and are never the only protection.
- S5: Prior design (odd/tasks/issue-23-agent-first-access.md, "S3 guarded writes"): fixed allowlist create/comment/log/assign/move/update, tool-specific idempotence documented honestly (create, comment and log are non-idempotent). Read-only mode must reject writes structurally, not through prompts.
- S6: Existing read tools, their metadata, relative order, instructions and the CLI behavior stay unchanged. Maintainable boundaries: small focused files, small consumer-defined interfaces, no growth of existing large files without reason.

- L4: Design from the explorer, accepted by the parent. With `--allow-writes` only, register `gojira_create`, `gojira_comment`, `gojira_log_work`, `gojira_assign`, `gojira_move`, `gojira_update`, `gojira_delete` in separate files (`writes.go`, `write_confirmation.go`); `Reader` stays read-only and a narrow consumer-defined write interface is added. Delete without a token returns a preview and a single-use token bound to action plus normalized key, stored only in memory, expiring in two minutes, with an injected clock; no mutation without a valid token. Result shape `{schemaVersion, action, issueKey?, mutationState, data?, code?, message?, hint?}`; no automatic retry; sanitized errors. Absent flag: golden surface and guide bytes unchanged.
- L5: Product questions were not answered by the user; the parent applies the explorer's conservative defaults and reports them: exclude sprint/backlog moves; create never adds to a sprint; move requires an unambiguous status and rejects ambiguity; update allows only safe scalar fields and never replaces the description; delete preview discloses only action and key, token lifetime two minutes; worklog and create are documented as non-idempotent and never retried.

- L6: Worker asked whether MCP assignment takes an accountId or an email. Parent decision: `gojira_assign` takes `{key, accountId}` and calls AssignIssue directly, because `gojira_users_search` already returns account IDs and email resolution is ambiguous when profiles hide emails. Email resolution stays CLI-only. This is a deliberate difference from the CLI, documented in the tool description and README.
- L7: Parent review of the first implementation. Finding: the delete confirmation token is returned to the same agent that requested the preview, so it forces a deliberate second call and blocks a one-call accidental delete, but it does NOT prove a human approved the deletion; a prompt-injected agent can redeem it. Documentation must say exactly that. A stronger guarantee would need client-side human approval (for example MCP elicitation where the client supports it); that is a separate product decision for the user and is not implemented here. Minor: the token was consumed before checking that a writer exists; test coverage for enabled schemas and mutation request bodies was not exhaustive.
